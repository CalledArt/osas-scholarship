# Controllers

## Every database round trip costs ~240ms — count queries, not milliseconds
The database is hosted on Supabase in ap-northeast-1 and reached through the pooler. A warm `select 1` measures ~240ms; opening a connection costs ~950ms. Page time is therefore (number of round trips) x 240ms, and almost nothing else — a DB-free page renders in 15ms.

So the only optimisation that moves the needle is removing round trips. Prefer one joined query over two eager loads, and reuse a collection you already loaded instead of re-querying it (the admin dashboard resolves recent applications' scholarships from the register it already holds).

Measured: admin dashboard went 1.93s -> 0.75s by dropping 2 queries, enabling DB_PERSISTENT, and unsetting the pgsql `charset`/`search_path` config keys (each of those made Laravel's connector run an extra SET statement per connection — one full round trip).

Caching is not the lever here: at 240ms per query the file cache already removes ~99.6% of the cost, so Redis would buy under 1ms over it and is not worth a dependency.

## Students apply to at most 2 scholarships and hold only 1 active; Ended frees a place
User::SCHOLARSHIP_LIMIT (2) caps a student's applications: pending and approved both count, rejected ones never count, and nothing counts once OSAS sets the scholarship to ScholarshipStatus::Ended (grant period over). User::ACTIVE_SCHOLARSHIP_LIMIT (1) caps active (approved, not Ended) scholarships: while a student holds one, remainingScholarshipPlaces() is 0, so they cannot apply to anything until it ends. Two pending applications can both pass, so the pass list (DecideScholarshipApplicationsFromCsv) also enforces it. A matched student already active on another scholarship is rejected with passed_while_holding_active set, takes no slot, is reported as already_active, and gets the ScholarshipApplicationRejected variant explaining why; their page says they passed. Closed only stops new applications, so approvals on a Closed scholarship are still "Active". ScholarshipApplicationPolicy::create enforces both limits. The student Dashboard and Scholarships page show Active scholarships first, then Available to apply (hidden at the limit). Closed scholarships the student never applied to are deliberately not listed for students. Republic Act 10931 (free tertiary education) heads Active while User::hasFreeTertiaryEducation(): year of study (school years since the 20YY entry year that student numbers start with; SY opens in August, User::SCHOOL_YEAR_START_MONTH; falls back to year_level) must not exceed program_years + 1, per Section 6(a)(3). program_years is set at registration and by OSAS in Edit Student Data, never by students. It is a fixed row (x-free-tertiary-education) linking to the Act's full text at scholarships.republic-act-10931, not a Scholarship record or application, and never counts toward either limit. That text is transcribed from the signed Official Gazette copy; common online copies (e.g. Lawphil) drop words and reverse Section 11, so never re-paste from them; it uses the green approved wash, not gold, which DESIGN.md reserves for pending. Pages compute both from User::scholarshipApplicationsWithScholarship() (one joined query) and remainingScholarshipPlaces(). Don't add a per-row query.

## The ~240ms round trip is the workstation, not production
The ~240ms per query above is local dev talking to Supabase in Tokyo. Production runs in hnd1 next to the database: measured 2026-10-16, a warm /login (PHP + 2 session queries) answered only ~30-50ms slower than a static robots.txt, and /up (Laravel boot, no DB) matched the static file. So in production a query costs a few ms; don't trade correctness or features for one round trip. What users do feel in production is cold starts (3.6-4.1s TTFB after idle). Don't switch SESSION_DRIVER to cookie for speed: the pass list flashes every decided applicant into `decisionResults`, which outgrows the ~4KB cookie limit and would silently vanish.

## Leave of absence pauses RA 10931, blocks scholarships and voids pending applications
users.student_status (App\Enums\StudentStatus: Active, LeaveOfAbsence) is set only by OSAS in Edit Student Data (UpdateStudentRequest); registration defaults to Active. While on leave, User::hasFreeTertiaryEducation() is false but isWithinFreeTertiaryEducationYears() is unchanged, so pages say RA 10931 is "paused", not "ended". The leave does not change the year-of-study count. remainingScholarshipPlaces() returns 0, so the policy, Available to apply and the apply form all refuse. Saving a student as on leave runs User::voidPendingApplications(). It sets ApplicationStatus::Voided on their pending applications, which frees those slots for other students. Scholarships already approved for the student are never voided (decided 2026-10-23); they stay active while the student is on leave. Setting the student back to Active never restores voided applications. Voiding never reopens a Closed scholarship; the save message tells OSAS which ones to reopen. The pass list voids any pending applicant on leave instead of deciding them. That only catches a submission made at the moment of the save. The passed_while_on_leave column was added and then dropped; don't bring it back.

## One open posting per preset; a student holds one posting per preset
scholarships.preset records the ScholarshipPresets key a posting came from (decided 2026-10-24). OSAS can't post a preset while another posting of it is still status Open (Scholarship::openFromPreset). The check runs in StoreScholarshipRequest, then again in ScholarshipController::store under Cache::lock("scholarships:post-preset:{preset}"), so two posts sent at once land only once. Reopening a closed posting is refused while another of its preset is open; an already-open posting stays editable. A student can't apply to a posting whose preset they already hold, meaning a pending or approved application on a scholarship that hasn't Ended (User::holdsPlaceFromPreset). Rejected and voided applications never block. This is enforced in ScholarshipApplicationPolicy::create, and again in the store transaction after lockForUpdate on the student's row. Available to apply hides those postings, and the scholarship page explains why. The migration backfilled preset once from stem_courses_only (dost) and the exact TDP/TES titles; apart from that one-time match and the open-title check below, nothing is decided by title. There is no unique index, because legacy duplicate open postings (two TDPs) existed when this was added.
